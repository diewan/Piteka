# Accountability fraud and abuse scenario matrix

Status: FRAUD-01 baseline, 2026-07-22. Piteka base revision:
`0f6dc23e3ea5a45e4209b36cf9c912a7f18032bf`.

This is a bounded risk catalog for the current deployment-accountability slice
and the already-planned investigation work. It is not an exhaustive catalog of
real-world fraud. It does not turn suspicious evidence into a finding of fraud,
and it does not treat integrity as truth.

## Interpretation rules

Risk is ranked by impact and likelihood within this slice: P0 can create or
conceal an unauthorized production action or cross a tenant boundary; P1 can
materially corrupt an investigation or deceive an approver; P2 is important but
normally requires another control failure to cause either result.

The classification and assurance verdict are deliberately separate:

- **Fraud** means evidence supports intentional deception; intent is an
  investigator finding, never inferred from a failed signature alone.
- **Error** means the same observable mismatch can be explained without intent.
- **Uncertainty** means available evidence supports incompatible explanations.
- **Absence of evidence** means a required fact is not available. It is never
  evidence of non-occurrence unless a verified completeness mechanism applies.
- Protocol verification may report `Valid`, `Invalid`, or `Indeterminate` for
  the applicable assurance dimension. Authority reconstruction may report only
  `Compatible`, `Incompatible`, or `Indeterminate`; it never reports
  “Authorized.”

“Owner” below owns the mitigating product or protocol work, not the truth of an
external claim. Test names are stable adversarial obligations. Existing tests
are linked by path; planned tests name the ticket that must add them.

## Coverage and ownership gates

Every P0/P1 row has an adversarial obligation above. A referenced planned test
is release-blocking for its ticket; the mapping is not evidence that the test
already exists. The dependency order remains FRAUD-01 → EVIDV2-01 →
AUTHREC-01/CASES-01 → ENT-01 → HEM-06. Product code must not implement local
substitutes for Parwana evidence or authority semantics while those protocol
tickets are pending.

This document introduces no runtime behavior, schema, canonical bytes, or
authority path. Rollback is removal of this document. No deployment order or
data migration applies. Future reviews must preserve historical scenario IDs;
retired scenarios should be marked retired with a reason rather than silently
deleted so test and incident references remain intelligible.
